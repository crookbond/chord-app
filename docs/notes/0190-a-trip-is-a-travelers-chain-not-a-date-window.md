**A trip is a traveler's own chain of connected legs, not a shared date window**: a prod audit of `ownertest@gmail.com`'s trips (18 rows) found both directions of the same defect. `findTripByDateRange` (`trips.service.ts`) matched purely on `[start_date, end_date]` overlap, scoped to the user's groups, tied-broken by closest start — no traveler, no place. A five-hop Kenya safari (Nairobi→Doha→Mara→Amboseli→Diani→Nairobi→JFK) split into five separate trips because each internal hop is a single non-overlapping day; meanwhile a spouse's unrelated three-day Amtrak weekend silently absorbed into a six-week in-law visit because the weekend's dates happened to fall inside the visit's (accidentally widened) window. Both are the same root cause: date overlap answers "what else is happening then," not "does this belong to the same trip" — the second question is about a specific person's own continuous travel.

**The new rule, in order:** (1) **person** — for one traveler, a leg extends whichever of their own trips it connects to by *city*, not exact airport-code equality (`sameMetro`, `kernel/airport-metro.ts` — already shipped for `get_trip_status`'s `legGaps`, now promoted from a display-only check to the actual matching primitive); a one-way with nothing to connect to is its own trip. (2) **group** — the scope a traveler's chain is searched within (their groups, current group preferred), never a substitute signal when the traveler is unknown. Nested same-person detours (a side trip in the middle of a longer visit) stay flat — one trip, ordered legs — rather than becoming a parent/child hierarchy, on the owner's call that nesting reads poorly on the Trips tab. Manual combine/split already exists and needed no new building: the Trips-tab drag-to-merge gesture, `merge_trips`/`move_leg`/`move_accommodation` bot tools, and `computeLegGaps`/`computeGaps` display checks (all shipped, commit `8920eb1` onward, previously undocumented — "ADR pending" in `airport-metro.ts`'s own header comment) are exactly the override path a person needing manual correction already has.

**No traveler, no guess — ask** (owner: "no different from how Claude asks when it needs a decision"): `findTripForTraveler` (`trips.service.ts`) requires a resolved `personaId` or an exact `passengerName` to chain against anyone's own travel; it never falls back to group-only or date-only placement once a trip has someone's legs on it. The live `add_travel_leg` bot tool refuses and asks when both `tripId` and `personaName` are absent (ADR 0100/0102's "refuse, don't confabulate" shape) — an explicit `tripId` is a deliberate override and skips the requirement entirely, since asking "who's on this" when the destination was already named is noise. The unattended paths (email body via `stageFlight`, uploaded-attachment via `ensureTripForFlight`) have no live turn to ask into, so an unidentified passenger gets the safe default — its own new trip, plus a posted note asking who it's for — correctable afterward with the already-existing `set_trip_passengers`/`merge_trips` tools rather than inventing a second pending-question queue for attachments (`pending-invites.ts`'s ADR 0166 shape is reserved for the live-chat case, where the model can hold the thread across a reply).

**One narrow exception found by the existing test suite**: a trip that has NO legs on it at all yet — a shell created ahead of any booking ("create a trip to Austin," then a bare "flying ORD→AUS" naming no one) — has nobody's travel to misattribute, so `findTripForTraveler` still checks it by date+group (`findEmptyTripInWindow`) when identity is absent or doesn't chain to anything. This is not the date-overlap bug returning: the risk that bug caused was an ALREADY-POPULATED trip silently absorbing a different person's travel, and an empty trip has no one on it to collide with. The same reasoning is why `add_travel_leg` only refuses-and-asks when even this fallback comes up empty, not the moment `personaName` is missing.

**Matching, precisely** (`chainConnects` in `trips.service.ts`): merge the traveler's existing legs on a candidate trip with the incoming leg(s) by `departAt`, and require every seam that touches a *new* leg to resolve `sameMetro(...) === true` — strict equality, not `computeLegGaps`'s tolerant `!== false`. The two checks answer different questions under different costs: `computeLegGaps` flags a break in an *already-one* trip, where an unresolved airport must never manufacture a false "your itinerary is broken" (ADR 0133's asymmetry); this decides whether to make two previously-separate trips *the same* trip, where an unresolved airport must never manufacture a false merge. A missed continuation costs one `merge_trips` tap; a wrong one silently glues two people's travel together. A leg already on the trip is filtered out before the seam check ever runs — a byte-identical re-send (a resent itinerary, a second passenger's copy of the same ticket, the exact case ADR 0185 covers) otherwise reads as a NEW leg competing with its own twin for the same departure instant, breaking a chain that is in fact perfectly intact. Two further seam-level refinements, both pulled from the real safari data: `WIL` (Nairobi's domestic strip, ~10km from the international `NBO` gateway) joins `NBO`'s metro in `airport-metro.ts` — both codes appear on real itineraries for what is unambiguously one city. And a seam `sameMetro` can't resolve on either side (a bush airstrip with no table entry — Mara-Keekorok, Amboseli) still connects when both legs print the exact same place text, since two identical strings are the same place regardless of the table's coverage; this can never manufacture a false merge the way a *fuzzy* fallback could, so it doesn't weaken the strict-`true` requirement.

**Accommodations have no traveler to chain on** (`Hotel`'s classifier schema carries no guest name, and `accommodations` has no persona column) — `findTripForStay` matches by **place** instead: the candidate trip's own `destination` or any of its legs' endpoints must `sameMetro` the stay's city (with the same exact-text fallback `chainConnects` uses, for a place with no table entry at all — a safari camp's address, not an airport or a city), scoped to one group, never cross-group, never by date overlap alone. New optional `city` field on `add_accommodation`/`AddAccommodationRequest` (distinct from the free-text `address`, mirroring the classifier's own `Hotel.city` field and its stated reason: naming a trip "Trip to Vail" rather than after whichever hotel happened to be booked last) — a live chat message with no city falls back to matching on `address`, then `propertyName`, in that order, same graceful-degradation posture as `hotelTripCity`.

**Completeness is a nudge, not a gate**: the `gaps` field (`computeGaps`, uncovered nights) already existed and was only ever surfaced on an explicit `get_trip_status` call. `add_travel_leg`'s result now reports any uncovered night on the affected trip right when a leg makes one visible. It stays a suggestion, never an error, because the system genuinely cannot know a gap is fine — Ben has a bed in both New York and Chicago, so no stay will ever exist for either leg of that trip, and that is correct, not incomplete. "Dismissed" needs no new state: `computeGaps` is pure date-interval coverage that doesn't inspect `propertyName`, so recording *any* accommodation for that span — including a placeholder like "own place" — permanently satisfies it. (This is already how a real family worked around the gap before this ADR: a chat-created stay literally named "home".)

**Prod backfill.** Existing trips are not re-grouped by the matcher change itself — the owner's framing: implement and verify first, backfill "once all satisfied." See the 2026-09-19 addendum for the one-time script.

Rejected: keeping `findTripByDateRange` as a fallback or for stay-nesting (owner: "just wrong — complete override" of trip/stay identity; it remains only for `add_reservation`/restaurant/movie placement into an already-known trip and `applyCancellation`'s already-narrowed lookup, neither of which is a *grouping* decision); guessing a traveler from geography/group when unidentified (the asymmetry above — a wrong guess is the exact failure this replaces); a parent/child trip hierarchy for a nested same-person detour (visually worse per the owner, and the flat model already renders correctly as an ordered leg list); an active search for a plausible unattached return leg when the user manually stitches two one-ways (owner: "just a nudge" — flag the gap, no auto-matching); resolving a passenger to a `personaId` before matching on the unattended email path (the classifier's `Flight.passengerName` is a raw string with no group-membership lookup wired into `trip-extraction.ts` today, and exact-name matching already closes the two prod cases audited — a fast-follow, not blocking this ADR).

**Addendum 2026-09-18 — verified against a full replay of the real prod data, not just the two audited cases.** `trip-prod-replay-ownertest.integration.test.ts` replays every real leg/stay for `ownertest@gmail.com` through the actual matcher, in the true chronological order each one arrived (`created_at`), using the real group membership (only John and Alice are Chord accounts anywhere — Ben, Nolan, Simon and Kate are always raw passenger-name strings). This is not the same as the two hand-picked cases above; it's every real leg, including the parts the original design conversation never got to see. It surfaced three findings the two-case audit missed:

1. **Real name-format variance defeated exact matching** — "SIMON STONE" (his Toronto ticket) never matched "STONE SIMON MR" (his Delhi↔New York ticket — the one prod filed onto the trip named "Trip to Washington, DC", which is Alice's Amtrak weekend, not his; word order swapped plus an added honorific), and "Ben" (a later chat restatement) never matched "Ben Doe" (the original booking). Fixed: `normalizePersonName` replaced by `namesMatch` — an order-independent token-SET comparison (honorifics stripped by `nameTokens`) as the primary rule, with a narrow, deliberately safer subset rule as fallback (a bare name matches a fuller one — "Ben" ⊆ "Ben Doe" — but ONLY when the subset resolves to exactly one identity among the traveler's own legs; two DIFFERENT full names that happen to share one word never collide, per this ADR's own asymmetry that a wrong merge costs more than a missed one). Fixing the name half then exposed a SECOND, independent bug in `chainConnects`'s duplicate-leg detection: two restatements of the identical Ben leg printed different UTC offsets for the exact same instant ("...T20:20:00-06:00" vs "...T21:20:00-05:00", both 02:20 UTC) — a raw string comparison read that as two different legs and rejected the chain on a false seam. Fixed alongside: `isSameLeg` and every `departAt`-based sort inside `findTripForTraveler`/`chainConnects` now compare by real instant (`departAtMs`, `new Date(...).getTime()` — epoch ms, UTC), never by string. That only works on strings that carry an offset — a bare "...T01:50:00" is read in the *server's* zone — and the attachment path's `ensureTripForFlight` was handing the classifier's deliberately bare ticket times straight in, so an identical re-upload never matched its stored (zoned) twin and minted a duplicate trip. It now zones the legs exactly as the caller does before storing them (`zonedDatetime`, airport IANA zone first, uploader's zone as fallback); the email path already did. The replay is now also faithful about WHO is on what: Alice's Amtrak weekend is the trip prod names "Trip to Washington, DC", Simon's Toronto trip and his Delhi↔New York ticket are one trip of his, and Kate (same flights, her own ticket) gets a trip of her own — person-first grouping, pinned as observed.
2. **Sparse passenger data makes the Kenya safari WORSE, not better: 8 trips, not the 5 in prod today.** Almost every internal safari leg (Doha→Nairobi, Nairobi→Mara, Mara→Amboseli, Amboseli→Diani, Diani→Nairobi) carries NO passenger name at all in the real classifier output — with no identified traveler, the city-matching machinery never runs at all (it only ever activates downstream of a known identity), so `WIL`/`NBO` and the exact-place-text fallback never get the chance to help. Left as a documented, known limitation — explicitly not the ADR 0190 conversation's scope, and not fixed here (the owner's call: name-format variance was worth fixing; this sparser, harder problem of a document naming no one at all was not asked for).
3. **A gap the original conversation never considered**: the 2027 Vail flight (into DEN) and its own hotel stay land on two different trips, because DEN and Vail genuinely are different metros — `sameMetro('DEN','Vail')` correctly says false, and there is no gateway-airport bridge for the "fly into DEN/SLC, drive the rest of the way" pattern `airport-metro.ts`'s own comment calls out. Owner's call: not a bug — getting from the airport to the resort is the traveler's own business, not something Chord needs to model, unless asked.

All three findings, including the two left unfixed, are pinned as literal assertions in `trip-prod-replay-ownertest.integration.test.ts` against the real prod values — not a synthetic approximation — so a future change to the matcher is checked against what this family's actual documents look like, not just the hand-picked cases that motivated the original design.

**Addendum 2026-09-19 — companions, closure, and the one-time regroup.** Three rules the first cut lacked, all now in one shared pure module (`server/src/services/trips/chain.ts`) so the live matcher and the prod script cannot disagree about what a trip is.

1. **Travelers on the same flight share a trip.** `sameFlight` = same route AND same *instant* of departure. `findTripForTraveler` checks this first, across every trip the user can reach and with no name needed: the family on one JFK→DOH ticket is one itinerary, and a strictly per-person rule split it into four trips (supersedes the earlier observation that Kate "gets a trip of her own"). Travelers who share nothing — Alice's Amtrak weekend — stay apart; that is the original bug and it stays fixed.
2. **A chain closes.** `chainSeams`: once a traveler's leg brings them back to where the chain started (by city), the next flight out of there is a NEW trip, not more of this one — otherwise LGA→DEN→JFK followed by LGA→LAX reads as one trip forever. The gap limit depends on what the next leg is: an *onward* connection may follow at most `MAX_ONWARD_GAP_DAYS` (30), the leg that *returns* home at most `MAX_RETURN_GAP_DAYS` (90; a semester away is a real trip). A single cap either chained Ben's 30 May arrival at LGA into the family's 1 Aug JFK→DOH (63 days, leaving from where he'd landed — not in transit, just home) or split a 57-day Chicago semester. The 30/90 values are judgement calls, not measured — a missed join costs one merge tap, a wrong one glues journeys together.
3. **One-time regroup for existing trips** (`services/trips/regroup.service.ts`, CLI `npm run regroup:trips --workspace=server`). Applies the same rules to what is already filed. **Plan-only unless `--apply`**; `--user <email>` / `--group <id>` to scope; one transaction per group; each applied group writes an undo file (`--undo <file>`); idempotent (a second plan has no ops). Conservative by construction: a leg with no named traveler is *pinned* in place (the sparse safari legs — finding 2 above — stay as they are); cancelled legs are never moved and don't hold a trip's date window open; a trip is owned by the cluster of its earliest-created clustered leg, so the survivor is the oldest owned trip; a trip whose legs all go to one survivor is *folded* (legs + stays + reservations + participants); duplicates (same flight, same traveler) are **reported, never removed**, because each leg owns a calendar event that would orphan; nothing is deleted — emptied sources are soft-deleted (ADR 0171). Verified against a copy of ownertest@gmail.com's actual prod grouping (`trips/__tests__/regroup.integration.test.ts`): Alice keeps her Amtrak weekend, the in-laws' Delhi tickets move to a trip of their own, the family Doha trip is untouched, Ben's May arrival is not folded into it. **Not yet run on prod** — the owner runs the plan first and approves the output before `--apply`.

**Addendum 2026-09-19 (2) — stays, bookings, pending bundles and cancellations follow the same rules.** Four places still used a date window or exact strings; each now uses the matcher's own rule.

1. **A stay matches by place AND dates** (`findTripForStay` takes the stay's check-in/out). Place alone glued a February 2027 Vail stay onto a February 2026 Vail trip in the same group (the replay only passed because the two lived in different groups); dates alone is the bug this ADR removes. The trip's window must overlap the stay's nights, and of several candidates the largest overlap wins, then the closest start. Consequence, flagged: the ADR 0173 test that put a Vail hotel into a pending DEN-flight bundle now yields two bundles — Vail and DEN are different places (owner: getting from the airport to the resort is the traveler's own business). The bundle-joining test now uses a Denver hotel.
2. **A booking reference is the booking** (`bookingId` in `trips/chain.ts`: ≥5 chars, never a placeholder like `N/A`, which every safari stay in the real data carries). Same reference ⇒ same trip (`findTripForTraveler`, checked after the shared-flight rule and before the chain rule), and a leg arriving with the same reference, same route (by city) and no visibly different traveler, at a new time within `MAX_RESCHEDULE_DAYS` (30 — owner-confirmed 2026-09-19, as is applying a schedule change directly with nothing to confirm), is the same flight **rescheduled**: `rescheduleBookedLegs` updates the leg and its calendar event in place instead of adding a duplicate. Applied directly on the email path (the notice is the evidence, like ADR 0168's cancellations) and inside `addTravelLeg` for the bot tool, proposal confirm and attachment path. Legs sharing the old time under one reference (a family on one flight) move together. **Not handled:** a route change under the same reference adds a leg.
3. **`findExistingLeg` uses the matcher's rules**: the same traveler by token-set/subset name or persona (`sameTravelerStrict`), the same route by city, the same instant regardless of printed offset. A different time on the same day is no longer a duplicate just because the flight number or reference matches (that is what hid a same-day move); only a few minutes' slop is formatting variance. Added the "<city> <airport>" spellings prod prints ("Chicago O'Hare International", "New York La Guardia") to `airport-metro.ts`.
4. **Pending bundles and cancellations stopped choosing by date.** `findPendingTripBundleId` (date overlap only — the Alice/in-laws bug one step earlier, on unconfirmed proposals) is replaced: a flight joins a pending bundle only as the same physical flight, the same booking reference, or the next leg of that traveler's own chain; a stay by place + dates. `applyCancellation` no longer picks one trip by `findTripByDateRange` first: `findLegsToCancelForUser` / `findAccommodationsToCancelForUser` search every trip the user can reach, by booking reference (cancelling every passenger on that booking) or, without one, by route + day (property + dates for stays) — and a flight two different travelers are on is **ambiguous and cancels nothing** without a reference. The cancellation classifier carries no passenger name, so per-passenger cancellation within one booking is not expressible yet.

**The regroup script joins on booking reference too** (owner: "it's a unique id for join — we should use it"): any two live legs in a group sharing a real reference are one cluster, whatever their routes, dates or named travelers, and a leg that names nobody is placed with its booking instead of pinned. The live matcher's booking step drops its traveler guard for the same reason, so the two agree; the guard stays only inside `rescheduleBookedLegs`, where it decides *which* leg moves, not which trip a booking is on.

**A route change under the same booking reference is detected, where the pairing is unambiguous** (owner: "if booking id is a join, and that gets route change, we can detect it exactly?" — yes, because the reference tells us exactly which legs are on file; the only question is how incoming legs pair with them). `reconcileBookedLegs` takes a whole document's legs for one booking on one trip and pairs them in order: (1) **unchanged** (same route by city, same instant) — nothing to do; (2) **moved** (same route, new time within 30 days) — updated in place with its calendar event; (3) **replaced**, only for callers holding the whole document (`allowRouteChange` — the email and attachment paths; a lone leg from the bot tool or a confirmed proposal cannot settle a route change and still adds): old and new legs pair only when the pairing is exact — a one-for-one leftover, a leg sharing an origin or destination with exactly one old flight (and that flight with only it), or equal counts that line up in date order with every pair plausible. Legs sharing the old time (a family on one flight under one reference) are replaced together. **Anything else is left alone and offered as an addition for a person to confirm** — an ambiguous new leg is never guessed onto an old one, and a leg the notice does not mention is **never removed** (silence is not a cancellation; the legs left unaccounted for are logged). Only legs whose traveler is not visibly a different person are considered, so one passenger's notice never re-routes another's legs. Limits: the whole-document assumption (a notice that lists only some legs is handled by the shares-an-end rule and otherwise falls through to an addition), and the email path only logs the unaccounted-for legs rather than raising a nudge.

# 0048 — Native deep-linking for invite links

**Status**: accepted
**Date**: 2026-06-10
**Related**: [ADR 0047 — Shareable group-invite links](./0047-shareable-join-links.md),
[ADR 0031 — UUID-referrer soft-link from TG welcome DM](./0031-uuid-signup-soft-link.md),
[ADR 0041 — Native iOS OAuth client](./0041-native-ios-oauth-client.md)

## Context

ADR 0047 shipped shareable `/join/<CODE>` links that point at the **web**
app, and explicitly deferred (alternative #3) making the link open the
*native* app on a device that has Chord installed — that needs Apple
Universal Links / Android App Links domain verification, which in turn needs
a stable production domain. We now have one: **`chordapp.ai`** (already the
`EXPO_PUBLIC_API_BASE` for every EAS profile). This ADR un-defers that work.

Goal: tapping `https://chordapp.ai/join/<CODE>` opens the Chord app if it is
installed (joining the group and dropping the user into the chat), and falls
back to the web app in a browser otherwise — with no separate link format.

## Decision

Use the platform-native verified-link mechanisms; keep the single
`https://chordapp.ai/join/<CODE>` URL for all surfaces.

- **iOS Universal Links** — `ios.associatedDomains: ["applinks:chordapp.ai"]`
  in `app.json`, plus a signed-association file at
  `https://chordapp.ai/.well-known/apple-app-site-association` scoping the
  `/join/*` path to the app's `appID` (`<TeamID>.app.chord.demo`).
- **Android App Links** — an `autoVerify` intent filter in `app.json`
  (`scheme https`, `host chordapp.ai`, `pathPrefix /join`), plus
  `https://chordapp.ai/.well-known/assetlinks.json` listing the app package
  and the **release signing cert's** SHA-256 fingerprint.
- **Association files live in `mobile/public/.well-known/`.** Expo copies
  `public/` to the web-export root, so the files ship with the same web
  deploy that serves `/join` — exactly the mechanism the privacy policy
  already uses (`public/chord-privacy-policy.txt`). No server route, no
  separate hosting step.
- **No client routing code.** Expo Router already owns `/join/[code]`; once
  the OS hands the verified URL to the app, Expo Router matches the path and
  renders the existing join screen. The signed-out → OAuth → resume flow
  reuses the AsyncStorage pending-code stash unchanged (ADR 0047 / 0031).
- **`inviteUrl()` stays the link builder.** It already resolves to an
  absolute `https://chordapp.ai/...` on native via `EXPO_PUBLIC_WEB_BASE`,
  now set on every EAS profile (the same domain the OS verifies against).

### Two secrets must be filled before verification works

The iOS `appID` is filled in (`5YLAQB2ZQZ.app.chord.demo` — Team ID
`5YLAQB2ZQZ`, "John Doe"; not a secret, fine to commit). The Android file
still carries a **placeholder** fingerprint, because that value is generated by
the signing keystore and isn't in the repo:

| File | Value | Source |
|---|---|---|
| `apple-app-site-association` | `5YLAQB2ZQZ.app.chord.demo` ✅ | Apple Developer portal → Membership → Team ID (not secret) |
| `assetlinks.json` | `REPLACE_WITH_ANDROID_SHA256_FINGERPRINT` ⬜ | `eas credentials` → Android → the release keystore SHA-256 |

Until the Android fingerprint is real, **Android** verification **fails
closed**: the link simply opens the web app (the ADR 0047 behavior). That is
the correct graceful degradation — nothing breaks, the native hand-off just
doesn't engage on Android yet. iOS is ready once the web app is deployed.

### Hosting requirements (outside the repo)

Whatever fronts `chordapp.ai` must serve both well-known files over HTTPS:

- **No redirect** on `/.well-known/apple-app-site-association` (Apple's CDN
  fetches it directly; a 301/302 fails verification).
- `apple-app-site-association` has **no file extension** and should be served
  as `application/json`.
- Both must be reachable at the apex `chordapp.ai`, matching the
  `applinks:` / intent-filter `host`.

## Alternatives considered

1. **Custom-scheme link (`chord://join/<CODE>`).** Works without domain
   verification, but a raw `chord://` URL is dead text in a browser, email,
   or on a device without the app — no web fallback. The whole value of ADR
   0047 is one artifact that works everywhere. Rejected; the custom scheme
   stays for OAuth only.
2. **A separate server route for the well-known files.** The Express app is
   API-only; adding static-file routes there couples the association files to
   the API process rather than the web deploy that actually owns the
   `chordapp.ai` document root. Putting them in `public/` keeps them with the
   thing they describe. Rejected.
3. **`app/+native-intent.ts` rewriter.** Only needed when the incoming path
   must be transformed before routing. `/join/<CODE>` already maps 1:1 to the
   route, so no rewrite is required. Not added.

## Implementation

- **Association files** — `mobile/public/.well-known/apple-app-site-association`,
  `mobile/public/.well-known/assetlinks.json` (placeholder IDs, see above).
- **Expo config** — `mobile/app.json`: `ios.associatedDomains` +
  `android.intentFilters` (autoVerify).
- **EAS env** — `EXPO_PUBLIC_WEB_BASE=https://chordapp.ai` added to the
  `development`, `preview`, and `production` profiles in `mobile/eas.json`.
- **Link builder** — unchanged `inviteUrl()` in `mobile/src/api.ts`.
- **Ops** — verification + test steps in
  [`docs/ops/native-deeplinks.md`](../ops/native-deeplinks.md).

### One canonical host

The web app, API, invite links, and the OS-verified deep-link host are all the
**apex `chordapp.ai`** — there is no `app.` subdomain. Four things must always
agree, so they're enumerated here as the single source of truth:
`ios.associatedDomains`, the Android intent-filter `host`, the `.well-known`
hosting target, and `EXPO_PUBLIC_WEB_BASE` (= `EXPO_PUBLIC_API_BASE`). Changing
the host means changing all four together.
